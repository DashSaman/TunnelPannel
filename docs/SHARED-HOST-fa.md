# نصب کنار سرویس‌های دیگر و تشخیص تداخل

مسیر پنل: **پرتال ← سرورها ← بررسی سرور ← تونل‌ها، پورت‌ها و سرویس‌های موجود**.
گزارش با زمان ثبت و در فضای همان مشتری نگهداری می‌شود. خواندن گزارش قبلی SSH
جدید نمی‌زند. هر جدول حداکثر۲۰۰ ردیف نشان می‌دهد؛ فایل دانلودی همه ردیف‌ها را دارد.
پیش از اولین ثبت منابع هر تست، هر دو سرور دوباره به صورت فقط‌خواندنی بررسی می‌شوند.
آماده‌سازی وابستگی WaterWall-H هم بررسی موفق لازم دارد.

موارد بررسی: پورت‌های TCP/UDP روی IPv4/IPv6، سرویس‌های فعال systemd، نام پردازش‌ها،
نگاشت پورت منتشرشده Docker/Podman، نام و نوع اینترفیس تونل، آدرس‌ها، همه جدول‌های
مسیریابی، قوانین مسیریابی، تعداد سیاست‌های XFRM، وضعیت forwarding و RAM در دسترس.
اینترفیس‌هایی مانند `sit0` پیش‌فرض کرنل‌اند؛ صرف وجود آن‌ها یا یک پردازش، اثبات
تونل فعال و عبور ترافیک نیست. تونل‌های قبلی خودکار به مالکیت پنل درنمی‌آیند و
بررسی آن‌ها را حذف، متوقف یا وارد تنظیمات پنل نمی‌کند.

آرگومان پردازش‌ها، متغیرهای محیطی، تنظیمات خصوصی WireGuard و وضعیت رمزهای XFRM
خوانده نمی‌شوند. stderr خارجی وارد گزارش نمی‌شود. ابزار مفقود، بررسی ناموفق
کانتینر، رزرو نامعتبر یا بررسی ناقص، اجرای تازه را مسدود می‌کند؛ سرور خالی فرض
نمی‌شود. روی Ubuntu24.04 خروجی سیاست‌های XFRM حتی با `ip -j` متنی است؛ شمارش
سیاست‌ها با خروجی متنی انجام می‌شود.

## پورت و سرویس مشترک

تخصیص‌دهنده اصلی، پورت اشغال، نگاشت کانتینر، منابع رزروشده پنل، فهرست ممنوع و
بازه‌های رزروشده مدیر را کنار می‌گذارد. هنگام هر تخصیص پورت، بررسی تازه انجام
می‌شود. یک شماره پورت در هر پروتکل، مستقل از آدرس bind، برای هر دو خانواده آدرس
محافظه‌کارانه اشغال محسوب می‌شود. انتخاب قبلی prefix، نام اینترفیس و شناسه‌های
مسیریابی نیز منابع موجود را در نظر می‌گیرد.

اگر سرویس IPsec، سیاست XFRM یا پورت/رزرو UDP500 یا4500 وجود داشته باشد، اجرای
تازه IKEv2/VTI/VTI6/L2TP متوقف می‌شود؛ حتی اگر IPsec قبلی متعلق به خود پنل باشد.
این محافظه‌کاری مانع تغییر daemon مشترک می‌شود و سازگاری تنظیمات دیگران را فرض
نمی‌کند. L2TP پورت ثابت UDP1701 را هم بررسی می‌کند. روش‌های HAJSAMAN در صورت
خاموش بودن IPv4 forwarding، اجازه فعال‌کردن سراسری آن را ندارند.

برای پورت‌های آینده یا پویا، روی **هر سرور مربوط** فایل معمولی JSON با مالکیت
root در `/etc/tunnelpannel/reserved-ports.json` بسازید:

```json
{"tcp": [18081, 18082, [22000, 22009]], "udp": [[10000, 20000]]}
```

این بازه‌ها نمونه‌اند و تنظیم واقعی تهران نتورک/مایتل فرض نشده‌اند. بازه واقعی
برنامه، مخصوصاً پورت‌هایی که هنگام نیاز باز می‌شوند، باید ثبت شود؛ اسکن نمی‌تواند
هر پورت آینده را خودکار پیش‌بینی کند.

نصب تازه ابتدا loopback8080 را بررسی می‌کند. اگر پیش‌فرض ضمنی اشغال یا رزرو باشد،
یک پورت آزاد از تخصیص‌دهنده اصلی انتخاب و در env و رسید نصب ذخیره می‌شود. پورت
صریح کاربر یا پورت ذخیره‌شده خودکار عوض نمی‌شود؛ تداخل با سرویس دیگر نصب را
متوقف می‌کند. نصب مجدد فقط وقتی پورت قبلی را متعلق به خود می‌داند که همه socketهای
TCP LISTEN همان شماره متعلق به MainPID سرویس API باشد. نگاشت کانتینر خارجی است.
پیش از بازنویسی واحد API دوباره بررسی می‌شود و سلامت، هم مالکیت socket سرویس
فعال و هم پاسخ HTTP را لازم دارد؛ پاسخ `/health` یک برنامه دیگر کافی نیست.

## منابع و محدودیت‌ها

مصرف مشاهده‌شده API در حالت بیکار حدود۱۱۶MiB بود؛ این عدد اوج مصرف نیست. برای
کنترلر کوچک، حدود۵۱۲MiB تا۱GiB **RAM آزاد اضافه بر مصرف برنامه‌های فعلی**، یک
هسته در دسترس و۲ تا۴GiB دیسک آزاد اولیه در نظر بگیرید. این‌ها برآورد برنامه‌ریزی
هستند؛ بار واقعی باید اندازه‌گیری شود. ساخت وابستگی‌ها و تعداد زیاد موتور آماده
را روی نود جدا انجام دهید؛ شروع با۲vCPU/۲GiB و برای ساخت سنگین یا هم‌زمانی،۴GiB
یا بیشتر مناسب‌تر است. سرور تست۱GiB با swap، حداقل امن برای تولید مشترک را ثابت نمی‌کند.

در بررسی فقط‌خواندنی مقصد مجاز تهران نتورک/مایتل،۲ هسته،۳٫۷۳GiB RAM با حدود۱٫۸۴GiB
در دسترس، حدود۱۶GiB دیسک آزاد،۱۰ کانتینر،۲۳ سرویس فعال و۳۱ اینترفیس از انواع تونل
دیده شد؛ تعداد اینترفیس شامل پیش‌فرض‌های کرنل است. پورت‌های80/443/9443 و نگاشت‌های
برنامه‌ها اشغال بودند. این بررسی چیزی را تغییر نداد. پیشنهاد، کنترلر فقط روی
loopback در کنار برنامه‌ها و اجرای تونل روی نودهای جداست؛ ظرفیت بار واقعی این
سرور هنوز آزمایش نشده و سازگاری همگانی تضمین نشده است.

قوانین سفارشی nftables/NAT، کانتینر rootless کاربر دیگر، namespace دیگر، سرویس
متوقف، پورت پویای آینده، کنترلر مستقل و مدیر هم‌زمان ممکن است رزرو صریح یا بررسی
دستی لازم داشته باشند. بررسی لحظه‌ای رقابت تا زمان bind را حذف نمی‌کند. هیچ
firewall سراسری پاک نمی‌شود و هیچ سرویس خارجی خودکار راه‌اندازی مجدد یا تصاحب نمی‌شود.

## پیش از حذف سرورهای تست

بکاپ معمولی شامل اطلاعات رمز‌شده سرورها، داده مشتری و هش دسترسی‌هاست، اما کلید
رمزگذاری نصب را ندارد؛ env/کلید همان نصب را جدا و خصوصی نگه دارید. نسخه هر دو
بکاپ، checksum، env جداگانه و اطلاعات تحویل مدیر روی کامپیوتر با Windows DPAPI
رمزگذاری و بازکردن و تطبیق آن آزمایش شد. بازیابی به همان حساب ویندوز/کامپیوتر
وابسته است. فایل‌ها خارج از Git هستند؛ پیش از از‌دست‌دادن آن حساب، نسخه قابل
انتقال با محافظت مستقل لازم است.

حذف سرور، خودِ endpoint تونل را از بین می‌برد؛ بکاپ پنل جای آن را نمی‌گیرد. در
انتقال، دو کنترلر فعال نباید روی صف و منابع بازیابی‌شده یکسان کار کنند. دسترسی‌ها،
ثبت عامل اختیاری، بررسی تازه و رسید واقعی روی endpointهای جدید باید تأیید شوند.

## آزمون انجام‌شده

نسخه کاندید روی **هر دو سرور تست۱۲ بررسی نام‌دار** را گذراند: چهار نوع پورت
IPv4/IPv6 TCP/UDP، شناسایی تونل و سرویس، عبور تخصیص از پورت اشغال، رد پورت صریح
متداخل، جابه‌جایی پیش‌فرض نصب تازه، رزرو بازه، توقف هنگام نبود ابزار، حفاظت IPsec،
مالکیت socket API، حفظ سرویس آزمایشی/API و پاک‌سازی فقط منابع همان آزمون.
فهرست اینترفیس‌های قبلی و هش ورودی، روش‌ها، حالت و PID گروه‌های فعال تغییر نکرد.
مبنای شروع این آزمون دو گروه با۱۰ عضو سالم بود؛ گروه تاریخی۷ عضوی قبلاً متوقف و
با گروه۵ عضوی failover جایگزین شده بود و بازسازی نشد.

حالت Docker NAT بدون socket و خطای خواندن، تست واحد دارند؛ دو نود canary فاقد
Docker بودند. نگاشت واقعی کانتینرهای مقصد مشترک بدون تغییر آن‌ها خوانده شد؛ این
بررسی، تست تزریق خرابی مصنوعی Docker نیست. نسخه نصب‌شده نهایی، CI و تصویر UI
در تحویل انتشار ثبت می‌شوند و از این آزمون کاندید استنتاج نمی‌شوند.
