# مهاجرت دروازهٔ موجود از پنل ادمین

پیاده‌سازی آماده است؛ نصب زنده و پذیرش دو سرور هنوز باقی است. این راهنما محدودیت CLI قبلی را برای مدیر سامانه تغییر می‌دهد. گروه‌های اصلی از قبل حسابداری دارند و دوباره مهاجرت نمی‌شوند.

با حساب مدیر سامانه وارد **https://tehnet.ir/tunnels/portal** شوید. در **مدیریت کاربران و فروش ← مهاجرت تونل‌های قدیمی** مشتری یا **مسیرهای خود مدیر** را انتخاب و روی مسیر ثبت‌شدهٔ زنده و فاقد حسابداری، **پیش‌بررسی و آماده‌سازی** را بزنید. تنظیمات تازه، دسترسی پین‌شده، مالکیت دروازه، سلامت/بیکاری، callback و شرایط حسابداری بررسی می‌شوند. روش‌ها، حالت و پین حفظ‌شده نمایش داده می‌شوند؛ اعتبار بررسی دو دقیقه است. مسیر متوقف یا دارای حسابداری مشخص است. تونل خارجی و خارج از مالکیت پنل وارد یا بازنویسی نمی‌شود.

یک بار **مهاجرت با حفظ تنظیمات** را بزنید. کار روی کنترلر اجرایی ادامه دارد؛ بستن صفحه یا تازه‌سازی، عملیات دیگری شروع نمی‌کند. پنل وضعیت را هنگام اجرا بررسی و تاریخچه را حفظ می‌کند؛ هم‌زمان فقط یک مهاجرت در هر نصب اجرا می‌شود. PID، هش تنظیمات و محل ثابت نجات در سرور تعیین می‌شوند و مرورگر امکان ارسال فرمان، رمز، مسیر فایل یا کانفیگ دلخواه ندارد. ادمین مشتری، اپراتور و مشاهده‌گر به این روال مدیر سامانه دسترسی ندارند. درخواست کوکی با CSRF و Origin موجود کنترل می‌شود.

دروازه منتظر دو نمونهٔ تازهٔ سالم و بیکار می‌ماند. تمام مقادیر تنظیمات، رمز ورودی، ترتیب/وزن اعضا، تقسیم بار/فیل‌اور و پین حفظ می‌شوند؛ تونل‌ها و رابط‌های زیرین بازسازی نمی‌شوند. TCP قبلی ممکن است نیاز به اتصال دوباره داشته باشد. نتیجه، تعداد نمونه‌های واقعی nonce و فاصلهٔ مشاهده‌شده بین پاسخ‌های موفق را نشان می‌دهد؛ قطعی صفر تضمین نمی‌شود. بک‌اند همچنان از دسترسی SSH پین‌شدهٔ ثبت‌شده استفاده می‌کند؛ مدیر به ترمینال SSH یا ورود دوبارهٔ رمز نیاز ندارد.

پیش از ارسال کار، کنترلر از دیتابیس عملیات، دیتابیس مشتری و registry نسخهٔ آنلاین رمزگذاری‌شده می‌گیرد و هش رمزگشایی را تطبیق می‌دهد. این نسخه‌ها در پوشهٔ خصوصی کنترلر می‌مانند؛ کلید نصب باید طبق روند بکاپ نصب جدا نگه داشته شود. helper موجود، فایل نجات/کانفیگ/مصرف معلومِ مبدأ را خصوصی برای root حفظ می‌کند؛ پنل آن‌ها را برای دانلود ارائه نمی‌دهد. بکاپ‌های ارتقای نصب جداگانه روی هر میزبان اصلی رمزگذاری می‌شوند. env، پرداخت و پلن مشتری تغییر نمی‌کنند.

ثبت مصرف از مهاجرت، بدون سقف و انقضای پنهان تا تخصیص مدیر شروع می‌شود. مصرف نامعلوم قبلی ساخته نمی‌شود؛ شمارندهٔ معلوم قبلی و مبنای جدا حفظ می‌شوند. تعیین سقف در همان دوره از **مصرف مشترک ماهانه** مصرف و اعتبار باز را نگه می‌دارد. وجود سقف واقعی قبلی، مهاجرت را رد می‌کند تا محدودیت بی‌صدا باز نشود. فضای مشتری غیرفعال نیز رد می‌شود.

اگر قطع شد، وضعیت را بخوانید و همان مسیر را دوباره **پیش‌بررسی و آماده‌سازی** کنید. نامزد رمزگذاری‌شدهٔ ناتمام با همان کلید ادامه می‌یابد؛ اگر دروازهٔ منطبق از قبل فعال شده باشد، بدون ری‌استارت دوباره پذیرفته می‌شود. اگر ثبت حسابداری تمام ولی ثبت نتیجهٔ عملیات قطع شده باشد، بازیابی از رسید رمزگذاری‌شده‌ای استفاده می‌کند که در همان تراکنش مسیر ثبت شده؛ هیچ فرمان SSH اجرا نمی‌شود. وضعیت زیر قفل پردازشی دوباره خوانده و پیش از آزادکردن قفل commit می‌شود تا نتیجهٔ موفق بازنویسی نشود. تلاش قدیمی که ادامه‌اش در عملیات جدید تمام شده، برچسب مناسب می‌گیرد. راه‌اندازی API هیچ مهاجرتی را خودکار شروع نمی‌کند. اگر مالکیت، تنظیمات یا شواهد ناتمام قابل تأیید نیست، شواهد خصوصی پشتیبانی را بررسی کنید؛ intent یا اعتبار worker نامطمئن را پاک نکنید.

API مدیر زیر `/api/billing/owner/workspaces/{workspace}/accounting-migrations` است؛ پیش‌بررسی در `/routes/{route}/preflight`، وضعیت در `/{operation}` و اجرا در `/{operation}/execute`. بدنهٔ POST یک شیء خالی است و فیلد اضافه رد می‌شود. پاسخ no-store و محدود به خلاصهٔ مجاز است؛ بکاپ خصوصی، token و traceback SSH منتشر نمی‌شوند.
